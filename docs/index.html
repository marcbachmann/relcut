Releases from conventional commits

Checked in review.
Released on merge.
Tokens out of reach.

Every pull request shows what merging it will release, and fails on a commit that is not conventional or a version outside the target branch's rules. On merge relcut ships it: a git tag, npm and GitHub Packages, a GitHub release with notes and assets. No dependency, script or git hook ever sees a token.

Either it fits you, or it does not

relcut is not an all-round tool. It does one way of releasing, and does it well. Here is the line.

It fits when

  • your history uses conventional commits: feat:, fix:, BREAKING CHANGE:
  • versions live in git tags, not in a committed package.json
  • you release from GitHub Actions to npm, GitHub Packages and GitHub releases
  • you want release branches that take backports
  • you want a release step that cannot run anybody's code with your tokens

It does not fit when

  • you need monorepos with packages versioned apart
  • you need prereleases (1.0.0-beta.1)
  • your release runs somewhere other than GitHub

There are no plugins: what relcut does not do is a step of your workflow. Another registry takes the tarball between prepare and publish; a CHANGELOG.md commit or an announcement comes after publish, with the outputs version, tag and notes, or in a workflow on the tag's push or on release: published.

Quick start

One workflow, no .releaserc, no plugins, nothing to install. A fix: releases a patch, a feat: a minor version, a BREAKING CHANGE: a major one. 

# .github/workflows/release.yml
name: Release
on:
  push:
    branches: [main]

jobs:
  release:
    runs-on: ubuntu-latest
    permissions:
      contents: write       # the tag and the GitHub release
      pull-requests: write  # comments on the released pull requests
      id-token: write       # npm trusted publishing
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
          filter: tree:0
          persist-credentials: false
      - uses: actions/setup-node@v5
        with: { node-version: 24 }
      - uses: marcbachmann/relcut@v1.0.0
        with:
          branches: main
          publish: npm

Three steps, one command

relcut release runs them all. Run them apart when something has to happen in between, or to check every pull request.

01 · check

Work out the version

Reads the commits since the last version tag, picks the next version and writes the release notes. Changes nothing, needs no credentials.

02 · prepare

Pack without tokens

npm ci --ignore-scripts, a rebuild for dependencies with install scripts, the version and a ci block into package.json, npm pack. No credential reaches any of them.

03 · publish

Tag first, then ship

Checks what it can, then tags and pushes, publishes the packed tarball, creates the GitHub release with its assets and comments on the released pull requests. Run again on the same commit, it finishes a release that failed after its tag.

Scenarios

Copy the one that matches. Each is a complete step; add actions/checkout with fetch-depth: 0, filter: tree:0 and persist-credentials: false before it. A shallow checkout gets a warning, and relcut fetches the history into it.

THE BIG ONE · RELEASE BRANCHES

Backports for older versions

main moves on. Users on 1.4 still get fixes, from a branch that can only release below what main released already. No setting says so: the tags do.

  • With main at v1.5.0, a fix: on release-1.4 releases v1.4.3.
  • A feat: there fails with v1.5.0 is not below v1.5.0, before anything is packed or tagged.
  • npm gets the dist-tag release-1.4, so a backport never moves latest back.
  • A branch without a release of its own fails once other branches released, instead of releasing 1.0.0.
  • The default branch is the trunk: when release-1.4 releases v1.4.3 first, main releases v1.5.0 at least.
  • Or let a commit cut the branch: a Release-Cut: release-1.5 footer on the first line of the commit's body creates it at the parent of that commit, in the same atomic push as the tag of main, whose release is a minor version at least. 
# cut the branch from the release it fixes
git switch -c release-1.4 v1.4.2
git push -u origin release-1.4
on:
  push:
    branches: [main, release-*]
jobs:
  release:
    steps:
      - uses: marcbachmann/relcut@v1.0.0
        with:
          branches: main release-*
          publish: npm
PULL REQUESTS

See what merging will release

The check's title shows the version, e.g. v1.4.3 · patch on release-1.4. The pull request fails before anyone merges:

  • on its own commits that are not conventional; history already on the branch is listed, never reported. conventional-commits: warn only warns.
  • on a version outside the target branch's rules, such as a feat: into release-1.4.
  • on a Release-Cut: or release: it asks for and relcut cannot follow. 
on:
  pull_request:
jobs:
  check:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      checks: write # the check's title shows the version
    steps:
      - uses: actions/checkout@v5
        with: { fetch-depth: 0, filter: tree:0, persist-credentials: false }
      - uses: marcbachmann/relcut@v1.0.0
        with:
          command: check
          branches: main release-*
          check-run-id: ${{ job.check_run_id }}
NPM

Trusted publishing, no npm token

npm exchanges the job's OIDC token for a short-lived one. Register the workflow as the package's trusted publisher on npmjs.com once. Needs npm 11.5.1 or newer and repository.url in package.json naming the repository, checked before the tag; more than one dist-tag needs 11.21.0, or an npm-token. With npm-stage: true the version waits in npm's stage queue until a maintainer approves it, which sets its one dist-tag; needs npm 11.15.0. 

permissions:
  contents: write
  pull-requests: write
  id-token: write
steps:
  - uses: marcbachmann/relcut@v1.0.0
    with:
      branches: main
      publish: npm
BINARIES

Assets on GitHub releases

relcut releases itself this way. Assets take an optional name, label and content type; the notes get a downloads table with every asset's size and SHA-256.

The option github-artifacts attaches artifacts of the same run to the release and needs actions: read. 

- uses: marcbachmann/relcut@v1.0.0
  with:
    branches: main
    github-assets: |
      dist/app-x86_64-linux
      dist/app-aarch64-darwin
      dist/SHA256SUMS
ON REQUEST

Release when you ask for it

With releases: explicit the commits wait until one asks: a release: commit or a Release: footer. Until then the check reads v1.5.0 · minor on next release. A release by hand is a commit too, made by a workflow_dispatch job. 

- uses: marcbachmann/relcut@v1.0.0
  with:
    branches: main
    releases: explicit
    publish: npm
STEPS APART

Build between prepare and publish

Use the version in your build, without any token in reach. Docker images and the rest can follow on the tag or release: published, with a token other than GITHUB_TOKEN so GitHub starts those workflows. 

- uses: marcbachmann/relcut@v1.0.0
  id: check
  with: { command: check, branches: main }
- if: steps.check.outputs.release == 'true'
  run: npm run build:docs
- if: steps.check.outputs.release == 'true'
  uses: marcbachmann/relcut@v1.0.0
  with:
    command: publish
    branches: main
    github-assets: dist/docs.zip
LOCAL

From your machine

Outside of Actions relcut takes the repository and branch from git and the token from gh auth token, and asks before it tags. Without a terminal and without --yes it refuses. 

$ relcut release --branches main --publish github
…
Publish v1.4.3 of acme/widgets from main (github)? [y/N]

What relcut guards against

A release step holds the keys to your package. relcut is built so nobody else's code gets near them.

Risk What relcut does
A dependency's install script reads your publish token npm runs without any variable whose name holds TOKEN, SECRET, PASSWORD or _AUTH. npm ci runs with --ignore-scripts; rebuild and pack run without credentials.
A script looks for the token in relcut itself relcut takes those variables out of its own environment, where ps and /proc would show them. On Linux nothing of the same user reads its memory, and npm runs with no_new_privs, so sudo is no way around it.
A script rewrites npm or node in the runner's tool cache prepare fingerprints node, the npm package and npm's global config before any package code runs. npm gets a token only while every byte still matches, and runs by its full path, never by whatever npm the PATH holds by then.
The checkout left the job token in .git/config prepare refuses to run npm and names the setting, never its value.
A git hook or a rewritten git config runs next to the push token git runs without hooks. Only ls-remote and push get the token, as a header through GIT_CONFIG_*, from a repository of relcut's own that reads no git config of the checkout, the user or the system.
A script leaves a process running that reads a later npm's environment Each npm that runs scripts leads a process group of its own, killed once it returns; on Linux relcut adopts every orphan of its scripts and ends every descendant. By default prepare then fails; side-effects: warn goes on. On macOS a process that left its group survives.
A script writes to the runner's env, path, output or summary file for later steps The scripts' npm gets none of those variables, and the files are put back once it returns. By default prepare then fails; with side-effects: warn the env and path lines come out as the outputs scripts-env and scripts-path.
A script plants a git or steers npm publish through files git is resolved and fingerprinted when relcut starts and run by that path. The npm that holds a token runs in a directory of relcut's own with a fixed environment; the registry comes from package.json as committed, verified object by object, and the tarball's publishConfig must match it.
A script prints ::add-mask:: or a fake ::error:: Workflow commands are stopped with a random token while npm and its scripts print.
A config file or plugin changes the release There are none. Settings come from flags and RELCUT_* variables only.
A newer commit landed during the release publish tags only while the branch still points at the released commit, in one atomic push that git refuses once the branch has moved. The next release takes those commits.
A release fails after its tag Assets, artifacts, the tarball and the npm dist-tags are checked before the tag. Running again on the same commit finishes a release that still failed: what is published stays, the rest is done.
A release is public before its assets With assets the GitHub release is a draft until they are uploaded.
A commit that is not conventional gets merged check fails the pull request on its own commits; history already on the branch never blocks a release.
A Release-Cut: or release: relcut cannot follow gets merged check fails the pull request on its own commits; on the branch it is a warning and never blocks the releases after it.
A cut moves a branch that is there The cut branch goes in the atomic push with the tag, leased as absent: one that exists stops the release before the tag.
A backport releases a version another branch released A branch releases only below the lowest version outside its history; constraint narrows it. check stops it.
A backport moves latest back A release below an existing version publishes under the branch's npm dist-tag, and its GitHub release never becomes the latest.
A flaky network fails a release halfway Requests retry and time out; pushes retry.
A damaged download of relcut, or one an earlier step wrote over The action checks the binary against the SHA256SUMS of the same release, fetched again on every run: a binary in the tool cache that no longer matches is downloaded again.

What no release step can guard inside one job: npm scripts run as the job's user. They get no token from relcut, but they can change files a later step runs or reads. relcut holds node and npm to their fingerprint from its own start, not before it. A release that must not trust its dependencies at all packs in a job without secrets and publishes in another.

What you get

~2 MB static binary

Linux builds are static and run on any runner image; macOS builds for arm64 and x64. Nothing to install on every run.

0 dependencies

relcut needs git, and npm only when it publishes to npm. The action needs node, bash and curl, all on every runner.

0 config files

Every option is a flag or a RELCUT_* variable, the same in the action, a workflow step and on your machine.

Reference

Every option is a flag, an action input and a RELCUT_<NAME> variable; a flag wins. relcut <command> --help lists what each command uses. To call relcut yourself, marcbachmann/relcut/setup only installs it onto the PATH.
